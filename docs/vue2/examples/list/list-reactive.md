# 响应式更新

**先说结论：大数据量的列表，不要放进 `data`（Vue 2 会深度观察它）。** 用 `shallowRef`
或 `Object.freeze` 的数组存列表，改数据时换一个新数组——自动更新照样生效，
而且不用付深度观察那笔账。

数据量小（几千条以内、更新也不频繁）就是另一回事了：放 `data` 里尽管改，
改一个字段就自动更新那一格，比什么都省事。下面按「为什么」→「小数据量怎么用」→
「大数据量怎么用」的顺序展开。

## 为什么不建议大列表放进 data

Vue 2 的观察是**预先**做的：`data` 里的数组一进来就被递归遍历，
每个元素的每个属性都被 `Object.defineProperty` 改写一遍。这笔账在数据进来那一刻就要付清，
之后每次读属性还要多走一层 getter——而虚拟列表恰好要频繁地整表读一遍：
高度实测（默认行为）下，每次数据变更都要扫完整个列表取 `itemKey`，重算总高度。

10 万条 × 6 个字段（Node 23 / arm64）：

| 列表存在哪 | 进来那一下 | 之后每次整表扫一遍 |
|---|---|---|
| `shallowRef` / `Object.freeze` 的数组 | 0.2ms | 0.8~1ms |
| `data` 里的普通数组（被深度观察） | **150~190ms** | 13~20ms |

1 万条的初始化是 16ms，1000 条是 2.9ms——**比例不变，绝对值才是关键**。

而这笔开销在虚拟列表里只换到「可视区那几十行能自动更新」：可视区之外的数据一次都没被渲染过，
深度观察为它们改写的 getter/setter 全部落空。数据每秒变好几次时，这笔账就直接压在帧上。

固定高度（`fixedSize`）不需要整表扫，开销小得多；但默认是高度实测。

## 数据量小，图省事：放 data 里

几千条以内，上面那笔是几毫秒，感觉不到。这时 `data` 是最省心的一档——
**改哪个字段就更新哪一格**，组件都不用通知：

```js
export default {
  data: () => ({ list: createRows(500) }),
  methods: {
    demo(newRow) {
      this.list[3].name = 'new';   // 那一格自己就变了（依赖收集直达插槽，连 setList 都不经过）
      this.list.push(newRow);      // 数组方法被劫持 → 长度变化被发现 → 新项出现
      this.list.splice(3, 1);      // 同上
    },
  },
};
```

这三种改法都不需要 `refreshItems()` / `forceUpdate()`。两处 Vue 2 自身的老限制照旧：
按索引整项赋值（`this.list[3] = obj`）和给已有对象**加新字段**不会被发现，用
`this.$set` 或 `splice` 代替。

## 数据量大：非响应式数据 + 换新数组

`shallowRef` 不观察数组内部，`Object.freeze` 的数组会被 Vue 2 直接跳过——两种都让读写回到原始速度。
代价是**任何原地修改都察觉不到**，不只是改字段，`push` / `splice` 也一样。
所以增删改统一换成新数组，一条规则覆盖所有情况：

```js
// vue 2.7 自带 composition-api；2.6 从 '@vue/composition-api' 引入
import { shallowRef } from 'vue';

const list = shallowRef(createRows(100000));

list.value = [...list.value, newRow];                                        // 增
list.value = list.value.filter((it) => it.id !== id);                        // 删
list.value = list.value.map((it) => (it.id === id ? { ...it, name } : it));   // 改
```

`.value` 换了引用会触发组件重渲染，组件随即把最新数据交给可视区内的每一项。
数据确实不经框架（外部 store 直写、WebSocket 推送后直接改对象）时，指明刷哪几项：
`refreshItems([changedId])`。

::: danger 这一档下的原地修改会「偶尔看起来能工作」
库持有的就是你传进来的那个数组对象，原地改动到的就是它。所以只要随后恰好发生一次滚动或
尺寸变化，新数据就会冒出来——但没有那次触发时它不会。这种时好时坏比彻底不工作更难查。
:::

## 示例在演示什么

示例刻意用 `shallowRef`（大数据量的那一档），好让「察觉不到」的情形看得见。
切换「更新方式」即可对比：

- **换新数组**（推荐）：`list.value = list.value.map(...)`。组件识别到 `list` 换了，
  把最新数据交给可视区内的每一项，行上的轮次跟着涨——不需要任何手动调用。
- **原地修改**：直接改某一项的字段。引用与长度都没变，`shallowRef` 又不观察数组内部——
  谁都察觉不到，行上的轮次会停住，点 `refreshItems()` 才追上。

数据放在 `data` 里的话，第二种也会自动跟上——那就是上面「数据量小」那一档的行为。

## 它是怎么知道数据变了的

库自己**不侦测**数据变化，一次都不——侦测交给框架，库只提供入口。`@virt-list/vue2` 内部就是一个 watch：

```js
// packages/vue2/src/VirtList.ts
watch([() => props.list, () => props.list.length], () => {
  vl.setList(props.list);   // 通知库：数据换了
});
```

它只比**两个标量**：数组引用和长度（`O(1)`，不遍历、不深比较）。所以：

- 换新数组 → 引用变了 → 发现 → 库把可视区内每一项的最新数据交还给插槽重新渲染
- 原地改字段 → 引用和长度都没变 → **发现不了**

被深度观察的列表还多一条更细的通道：挂载器给每个挂载点开了一个 Vue 实例，插槽读到的是被观察的属性，
改它由依赖收集直接更新那一格，连这个 watch 都不经过。这条通道就是「数据量小图省事」那一档的底层机制，
也正是它按全量数据收费。

滚动与尺寸上报不走这两条路，所以这套机制不影响滚动性能。

## 三种更新手段的分工

| 手段 | 什么时候用 | 范围与代价 |
|---|---|---|
| **自动**（推荐） | 换新数组，或深度观察下的任意改法 | 可视区内每一项，**原地更新**内容，DOM 全部复用 |
| `refreshItems([key])` | 原地修改，且框架察觉不到 | 只动指定的那几项，重建它们的 DOM |
| `forceUpdate()` | 兜底：不确定哪几项变了，或所有项的高度同时变了（如批量折叠） | 全部可见项，重建 DOM |

`forceUpdate()` 是范围最大的一个，重建可见项的全部 DOM。能指明 key 时优先用
`refreshItems([key])`，长列表里差别看得出来。
